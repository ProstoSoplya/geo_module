# ЧАСТЬ 2. Технический аудит

## 2.1. Узкие места производительности

### P1. (HIGH) BVH-сцена строится ДВАЖДЫ за один анализ
- `registration.py:365–367` — `RaycastingScene` строится в `register_pipeline`,
  используется для выбора победителя и для `_c2m_stats_down`.
- `deviation.py:57–59` — `compute_deviations` строит **новую** `RaycastingScene`
  на том же меше.

`add_triangles(...)` на большом меше — O(N_tri log N_tri), может занимать
секунды. Заголовок `registration.py:9` обещает «BVH строится 1 раз», но это
верно только внутри `register_pipeline`.

**Impact:** для меша ~1M треугольников экономия 2–5 секунд на каждом анализе.

**Где исправить:**
- Изменить сигнатуру `compute_deviations(..., scene=None)` — принимать готовую.
- В `worker.py:_run_pipeline` сохранить scene из register_pipeline и
  передавать дальше.
- Альтернатива: вернуть `scene` пятым/шестым элементом из `register_pipeline`.

### P2. (HIGH) `copy.deepcopy` облаков точек — ~7 раз за один прогон
- `registration.py:206` — в `_evaluate_candidate` (× N_hypotheses)
- `registration.py:215` — там же
- `registration.py:344, 345` — `pcd_full_aligned`, `pcd_down_aligned`
- `registration.py:485` — `_c2m_stats_down` (× 2 вызова)

При 9 гипотезах: ~20 deepcopy. Для 500k точек × 32 байта = ~16 МБ на копию,
итого ~320 МБ аллокаций за один анализ. GC-нагрузка + кэш-промахи.

**Что делать:**
- В `_evaluate_candidate` deepcopy нужен только из-за `.transform(...)`.
  Если хранить **точки как numpy**, преобразование делается без копирования
  Open3D-структуры — `points @ T[:3,:3].T + T[:3,3]`. Получаем массив, не
  PointCloud — но `scene.compute_distance` принимает Tensor из массива.
- Для `pcd_full_aligned` и `pcd_down_aligned` — deepcopy нужен один раз
  на пайплайн (там точки в дальнейшем модифицируются `.transform`). OK.

**Impact:** 30–50% сокращение времени фазы «выбор гипотезы» для больших облаков.

### P3. (MEDIUM) `pcd_full.estimate_normals` лишняя
`registration.py:82` — `pcd_full.estimate_normals(...)`. Для Point-to-Plane ICP
нужны нормали **target** (mesh-облака), а не source (`pcd_full`). 
`mesh_pcd_full` получает нормали через `use_triangle_normal=True` при семплировании
(строка 74). Open3D `TransformationEstimationPointToPlane` использует
**target.normals**.

**Проверить:** удалить `pcd_full.estimate_normals(...)`, прогнать тесты.
Экономия ~0.5–2 сек для крупных облаков.

### P4. (LOW) `sample_points_uniformly` на меше — дважды
`registration.py:71, 75` — `mesh.sample_points_uniformly(...)` вызывается
дважды (для full и для down). Это семплирование O(N_tri), не критично,
но можно сделать один раз для большего числа точек и затем `voxel_down_sample`.

### P5. (LOW) `_pcd_to_pv` копирует точки даже если их меньше лимита
`viewer_widget.py:218–231` — точки и отклонения копируются. Для просмотра
дополнительная копия не нужна, можно работать с view.

### P6. (INFO) LUT-раскраска в `deviation.py:colorize_point_cloud`
**Эффективна.** `_LUT_CACHE` хранит палитру, индексация векторизована, без
поэлементных Python-циклов. Узким местом не является.

## 2.2. Обработка ошибок и edge cases

### E1. (CRITICAL) Отмена анализа НЕ работает посередине ICP
- `worker.cancel()` ставит `_cancelled = True`.
- Проверка `_cancelled` происходит ТОЛЬКО в `_emit_progress`.
- Прогресс отправляется между этапами, а внутри `registration_icp` —
  это блокирующий C++-вызов без обратных вызовов.
- Поэтому отмена применяется в лучшем случае через 5–60 секунд (когда ICP
  закончится сам или сработает 60-секундный таймаут).

**Где починить:**
- Worker не может «убить» C++-поток Open3D, это принципиально.
- Минимум: показывать пользователю «Отмена будет применена после окончания
  текущего ICP-прохода» (сейчас сообщение «ожидайте» есть, но без таймера).
- Опционально: уменьшить `max_iteration` в грубом проходе с 80 → 40, чтобы
  каждый «отрезок» был короче.

### E2. (CRITICAL) ICP-таймаут оставляет «висячий» поток
`registration.py:223–243` — `_icp_with_timeout` использует
`ThreadPoolExecutor(max_workers=1)`. На таймауте:
```python
finally:
    executor.shutdown(wait=False)
```
**Проблема:** `shutdown(wait=False)` НЕ отменяет уже запущенную задачу. ICP
продолжает грузить CPU в фоне, пока не закончится. Если пользователь запустит
новый анализ — будут конкурировать два ICP.

**Что делать:**
- Документировать в коде: shutdown(wait=False) — намеренно «отпускаем»
  поток, чтобы не блокировать UI. Принять как trade-off.
- В UI: отключить кнопку запуска анализа на N секунд после таймаута/отмены.

### E3. (MAJOR) Таймаут 60 сек захардкожен
`registration.py:460` — `timeout=60`. Для меша 5М треугольников + облака 5М
точек 60 сек заведомо мало (один проход ICP может занимать минуты).

**Что делать:** вычислять таймаут пропорционально размеру данных или вынести
в конфиг (например, `registration.icp_timeout_sec`).

### E4. (MAJOR) Нет проверки NaN/Inf в координатах
Нигде не проверяется: `np.isfinite(points).all()`. Если в PLY-файле есть NaN
(встречается при разрушенных сканах), последующий KDTree, ICP и compute_distance
дадут непредсказуемые результаты или зависнут.

**Где добавить:** `project_manager.load_scan` — после
`o3d.io.read_point_cloud`:
```python
pts = np.asarray(pcd.points)
if not np.isfinite(pts).all():
    n_bad = int(np.sum(~np.isfinite(pts).all(axis=1)))
    raise ValueError(f"В скане {n_bad} точек содержат NaN/Inf...")
```

### E5. (MAJOR) Пустое облако после SOR — пропускается, но дальше упадёт
`preprocessing.py:39–41` — если меньше 10 точек, SOR пропускается, но
`voxel_downsample` потом тоже даст пустой результат → `pcd_down`
с нулём точек → дальше в `register_pipeline` всё развалится без
информативной ошибки.

**Что добавить:** в `worker._run_pipeline` после `preprocess_pipeline`
явная проверка `len(pcd_clean.points) >= 50` с понятной ошибкой
«Облако точек практически пустое после предобработки».

### E6. (MAJOR) Вырожденный меш — обрабатывается частично
`dimensions.py:96–107` — `compute_dimensions` корректно откатывается на AABB
при ошибке OBB. **Хорошо.**
Но `register_pipeline` не проверяет, что `mesh.vertices` ≥ 4, а
`_compute_adaptive_params` упадёт на пустом меше при делении на ноль
(`bbox_diag = 0` ⇒ радиусы 0 ⇒ `compute_fpfh_feature` сбой).

**Где добавить:** в начале `register_pipeline` — guard
`if bbox_diag < 1e-6: raise RegistrationError("Меш CAD-модели вырожден")`.

### E7. (MINOR) Если ICP сошёлся с `fitness=0` — обработки нет
В `_icp_two_pass` нет проверки `r2.fitness > 0`. Если RANSAC + ICP не нашли
ни одного inlier-соответствия, `r2.transformation = identity`. Регистрация
формально «удалась», но C2M-RMSE будет огромным.
**Сейчас:** ловится через `registration_suspect` — приемлемо, но молчаливо.

### E8. (MINOR) `_make_loading_dialog` — `OSError` глушится без сообщения
`main_window.py:953–956` — при ошибке `os.path.getsize(path)` возвращает None
без лога. Сам диалог не показывается — пользователь увидит «зависший» UI.

### E9. (INFO) `tests/fixtures/` создаётся только при запуске standalone
`test_registration_robustness.py:_generate_fixtures` вызывается только в
`if __name__ == "__main__"`. Под pytest fixture-файлы не создаются — это
не баг, но может удивить.

## 2.3. Thread safety

### T1. (OK) QueuedConnection — явно установлен
`main_window.py:482–487` — все 5 сигналов worker'а подключаются с
`Qt.ConnectionType.QueuedConnection`. **Корректно.**

### T2. (OK) GUI из worker — НЕ происходит
Worker не импортирует ничего из `ui/`. Общение строго через сигналы.
**Корректно.**

### T3. (MEDIUM) Race condition: `_cancelled` без блокировки
`worker.py:64, 69, 73` — `self._cancelled = True` устанавливается из главного
потока, читается из worker-потока. Запись/чтение bool в CPython атомарны
(GIL), но семантически это не задокументировано.

**Что делать:** добавить комментарий «опираемся на GIL для атомарности
чтения/записи флага» или использовать `threading.Event()` для явности.

### T4. (MAJOR) Race: повторный запуск анализа до завершения worker'а
`run_analysis` не проверяет `self.worker.isRunning()`. Если кнопка не
заблокирована (например, из-за `processEvents` или редкого пути), можно
запустить второй worker, создав параллельный анализ. Старый worker станет
«сиротой».

**Где починить:** в начало `run_analysis`:
```python
if self.worker and self.worker.isRunning():
    return  # уже идёт анализ
```

### T5. (OK) Visiteur кнопки `cancel` — лочится сразу
`cancel_analysis:497–498` — обе кнопки отмены отключаются до вызова
`worker.cancel()`. Повторный клик невозможен. **Корректно.**

### T6. (MEDIUM) `closeEvent`: `worker.wait(3000)` не гарантирует завершения
`main_window.py:996` — если worker не завершится за 3 сек (например, длинный
ICP), Qt-окно закроется, но worker-поток останется. На Windows это редко
приводит к visible-проблеме, но процесс не завершится «чисто».

## Вопрос 3. «Точка посередине тонкой стенки — как определяется знак?»

### Текущая реализация — `deviation.py:compute_deviations`

**Ветвь watertight (рекомендуемая):**
- `compute_signed_distance` — winding-number-знак. Корректен для срединных
  поверхностей тонких стенок.
- `ambiguous_mask` = точки, где эвристика (нормаль ближайшей грани) расходится
  с winding-знаком. Эти точки в 3D-виде окрашиваются серым.
- Sanity-check: если расхождение |sd| vs unsigned-dist > порога — варнинг в лог.

**Ветвь не-watertight (fallback):**
- Знак — только по `dot(vector_to_point, normal_of_closest_face)`.
- `ambiguous_mask = abs(cos_angle) < 0.05` — точки у рёбер/кромок (вектор
  почти в плоскости грани).
- **Срединную поверхность тонкой стенки эта эвристика НЕ ловит** — там
  вектор перпендикулярен поверхности с обеих сторон, dot не близок к нулю.

### Корректность

**Watertight ветвь — корректна.** Winding-number устойчив на срединных
поверхностях; ambiguous_mask маркирует именно те точки, где знак неоднозначен.

**Не-watertight ветвь — НЕЭФФЕКТИВНА на тонких стенках.** Порог 0.05 —
эвристический; на ребре куба cos=0, отлично ловится. На срединной поверхности
стенки толщиной 1 мм при отступе ±0.5 мм по нормали — cos≈1, эвристика
«уверена», но знак почти наверняка неверный.

### В отчёте PDF про «серые» точки — нет объяснения

`report.py` не упоминает `ambiguous_mask` нигде. В таблице статистики поля
`ambiguous_sign_count`/`pct` тоже не выводятся.

### Конкретные доработки

**Д3.1. Объяснить «серые» точки в UI и PDF**

## Вопрос 6. «Состояние расширенного режима утекает в базовый» — БАГ

### Воспроизведение

1. Пользователь A открывает приложение, конфиг = defaults (из `main.py:299`):
   `sor_neighbors=20`, `voxel_size=0`, `icp_coarse_pct=5.0`.

3. **При закрытии** программа сохраняет конфиг (`main_window.py:1031` —
   `self.manager.save_config("config.json")`). Изменённые значения
   уезжают в `config.json`.
4. Пользователь B открывает в базовом режиме. `load_config` (`main.py:292`)
   делает `_deep_merge(defaults, config)` — значения из `config.json`
   **перекрывают defaults**.
5. В UI расширенные секции **скрыты** (`_apply_mode(False)`), но
   `self.config` уже содержит «странные» значения.
6. Анализ запускается. `worker` читает `self.config` → использует
   `sor_neighbors=5`, `icp_coarse_pct=15` (см. `_run_pipeline`).

**ПОДТВЕРЖДЕНО.** Сейчас в репозитории `config.json` уже искажён:
`sor_neighbors=21`, `sor_std_ratio=0.5`, `icp_coarse_pct=3.5`,
`icp_fine_pct=1.3`, `icp_max_iter=90`. Это **не** дефолты `main.py`.

### Единственное место, где сейчас есть сброс
`panels.py:_on_mode_changed` (строка 338–345) — при выходе из расширенного
режима сбрасывает **только** `alignment_mode → "best_fit"`. Все остальные
параметры остаются.

### Решение

**Варианты:**

**Вариант A.** При переключении в базовый режим сбрасывать ВСЕ расширенные
параметры на defaults.
- ❌ Минус: пользователь может теряет тонкие настройки, которые подходят
  именно его оборудованию (например, для шумных сканеров `sor_neighbors=30`).
- ✓ Плюс: гарантирует воспроизводимость.

**Вариант B.** Хранить два набора параметров: `basic_defaults` и `advanced_overrides`.
В базовом режиме всегда использовать `basic_defaults`. В расширенном —
накладывать `advanced_overrides` поверх.
- ✓ Минус: усложняет config.
- ✓ Плюс: не теряются настройки пользователя.

**Вариант C (РЕКОМЕНДУЕМЫЙ).** В базовом режиме при запуске анализа
**временно** подменять параметры алгоритмов на defaults, игнорируя
содержимое `config.json` для секций `preprocessing`/`registration` (кроме
`alignment_mode`, который пользователь видит косвенно через UI).
- ✓ Плюс: пользователь B всегда получает «коробочное» поведение, даже если
  на той же машине работал пользователь A в расширенном режиме.
- ✓ Плюс: при включении расширенного — параметры из конфига возвращаются
  на UI (можно «настроить и сохранить» как раньше).
